🔧 Những gì đã được thay đổi

Đây là tóm tắt toàn bộ thay đổi so với code gốc ban đầu. Dùng để giải thích với giáo viên khi cần.

1. Thêm RabbitMQ — Async Messaging

Vấn đề cũ: Spring Boot gọi trực tiếp HTTP sang Node.js để gửi thông báo → 2 service phụ thuộc chặt vào nhau (tight coupling).

Giải pháp: Dùng RabbitMQ làm trung gian. Spring Boot publish message vào exchange, Node.js consume message và đẩy thông báo realtime qua Socket.IO.

File đã sửaThay đổi
backend/spring-boot-api/pom.xmlThêm dependency spring-boot-starter-amqp
backend/spring-boot-api/.../config/RabbitMQConfig.javaFile mới — cấu hình Exchange, Queue, Binding
backend/spring-boot-api/.../services/NotificationService.javaViết lại — dùng AmqpTemplate thay vì HTTP call
backend/nodejs-service/src/server.jsThêm connectRabbitMQ() — consume queue, emit socket
backend/nodejs-service/package.jsonThêm amqplib
docker-compose.ymlThêm service rabbitmq

2. Thêm Circuit Breaker — Resilience4j

Vấn đề: Nếu RabbitMQ hoặc VNPay bị lỗi, toàn bộ request booking/thanh toán sẽ fail theo.

Giải pháp: Annotation @CircuitBreaker bảo vệ các method quan trọng — khi lỗi quá nhiều, circuit mở ra và chạy fallback (ghi log, không crash).

File đã sửaThay đổi
pom.xmlThêm spring-cloud-starter-circuitbreaker-resilience4j, Spring Cloud BOM 2023.0.3
NotificationService.java@CircuitBreaker(name="notification", fallbackMethod="notifyFallback")
application.propertiesCấu hình threshold, window size, wait duration cho 2 circuit breaker

3. Thêm Distributed Tracing — Zipkin

Là gì: Tự động theo dõi mỗi request đi qua Spring Boot mất bao lâu, ở bước nào. Không cần viết thêm code.

RabbitMQ — Luồng hoạt động chi tiết

1. Student đặt phòng → BookingController.create()
   ↓
2. Spring Boot confirm booking
   ↓
3. NotificationService.notify(landlordId, "BOOKING_CREATED", ...)
   ↓  [@CircuitBreaker bảo vệ]
4. amqpTemplate.convertAndSend("saf.booking", "booking.BOOKING_CREATED", payload)
   ↓  [RabbitMQ Topic Exchange]
5. Queue "saf.notification.queue" nhận message
   ↓  [Node.js consumer]
6. channel.consume() → parse JSON → io.to("user_123").emit("notification", data)
   ↓  [Socket.IO]
7. Trình duyệt landlord nhận thông báo realtime 🔔

Circuit Breaker — Khi nào kích hoạt

Cấu hình notification circuit breaker:
  - sliding-window-size: 10 request gần nhất
  - failure-rate-threshold: 50% (≥5 lỗi → mở circuit)
  - wait-duration-in-open-state: 30s (sau 30s thử lại)

Trạng thái:
  CLOSED → bình thường, mọi call đi qua
  OPEN   → lỗi quá nhiều, chạy fallback (ghi log WARNING)
  HALF_OPEN → thử lại sau 30s, nếu OK → CLOSED lại

Kết quả: booking vẫn thành công dù RabbitMQ bị lỗi

❓ Câu hỏi giáo viên hay hỏi

Dự án anh dùng kiến trúc gì? Tại sao chọn Microservices?
Dự án dùng kiến trúc Polyglot Microservices — 5 service độc lập, 2 ngôn ngữ (Java + Node.js), 2 database (MariaDB + MongoDB), giao tiếp qua API Gateway và RabbitMQ. Chọn vì bài toán có 2 domain tự nhiên tách biệt: nghiệp vụ phòng trọ (Spring Boot phù hợp do JPA/Hibernate) và realtime chat (Node.js phù hợp do event-driven Socket.IO), dùng chung thì sẽ conflict về tech stack.
Microservices của anh giao tiếp với nhau bằng cách nào?
Hai cách: (1) Synchronous — Client gọi qua Nginx API Gateway, gateway route đến đúng service theo path prefix. (2) Asynchronous — Spring Boot publish message vào RabbitMQ Topic Exchange (saf.booking), Node.js subscribe và consume để đẩy thông báo realtime Socket.IO đến client. Async messaging giúp 2 service hoàn toàn loose coupling — Spring Boot không cần biết Node.js đang chạy ở đâu.
Circuit Breaker là gì? Anh dùng ở đâu?
Circuit Breaker là pattern bảo vệ hệ thống khi một service phụ thuộc bị lỗi — giống như cầu dao điện. Tôi dùng Resilience4j @CircuitBreaker trên NotificationService.notify(): khi RabbitMQ bị lỗi ≥50% trong 10 request, circuit mở ra và chạy notifyFallback() thay vì crash. Kết quả: booking vẫn thành công, chỉ mất thông báo tạm thời — user experience không bị ảnh hưởng.
Distributed Tracing là gì? Anh show được không?
Distributed Tracing theo dõi một request đi qua nhiều service, đo thời gian từng bước. Tôi dùng Micrometer Tracing + Zipkin. Mở localhost:9411 → Run Query → thấy danh sách trace → click vào 1 trace → thấy waterfall chart từng bước trong Spring Boot (HTTP filter → controller → service → database). Không cần viết 1 dòng code nào — auto-instrumentation.
Tại sao dùng 2 database khác nhau?
MariaDB (quan hệ) phù hợp cho dữ liệu có schema cố định, cần transaction ACID: users, rooms, bookings, payments — cần JOIN, foreign key. MongoDB (document) phù hợp cho chat: mỗi conversation có cấu trúc khác nhau, cần ghi nhanh, scale horizontal tốt hơn. Đây là Polyglot Persistence — chọn database phù hợp với từng domain thay vì ép dùng 1 loại.
API Gateway có tác dụng gì?
API Gateway (Nginx) là single entry point duy nhất — client chỉ cần biết 1 địa chỉ (localhost:80), không cần biết bên trong có bao nhiêu service. Gateway làm 3 việc: (1) Routing — phân phát request đến đúng service theo path. (2) WebSocket proxy — forward Socket.IO handshake và connection. (3) Serve static files — trả HTML/CSS/JS của React app trực tiếp, không cần qua backend.
Nếu 1 service bị down thì sao?
Tùy service: Nếu ai-chat-service down → chỉ mất tính năng AI chatbot, còn lại hoạt động bình thường. Nếu nodejs-messaging down → mất realtime chat và notification, nhưng booking/auth vẫn chạy. Nếu RabbitMQ down → Circuit Breaker kích hoạt, notification bị bỏ qua nhưng booking vẫn thành công. Đây là lợi thế của Microservices so với Monolithic — một phần fail không kéo sập cả hệ thống.
Sự khác biệt so với Monolithic là gì?
Monolithic: 1 codebase, 1 database, 1 process — đơn giản hơn nhưng scale khó, deploy phải stop toàn bộ, 1 lỗi có thể crash toàn app.

SAF Microservices: 5 service độc lập, có thể scale riêng từng service (Node.js scale theo chat load, Spring Boot scale theo booking load), deploy từng service không ảnh hưởng service khác, mỗi team có thể dùng tech stack riêng.
Làm sao biết tất cả service đang chạy ổn?
Hai cách: (1) docker-compose ps — xem tất cả container, status phải là (healthy). (2) Spring Boot Actuator — localhost:8082/actuator/health trả JSON chi tiết tình trạng database, RabbitMQ, disk. Docker dùng endpoint này để tự động health check và restart container nếu unhealthy.

• RabbitMQ → localhost:15672 → tab Queues → thực hiện 1 booking → thấy message count tăng

• Circuit Breaker → localhost:8082/actuator/circuitbreakers → xem trạng thái
