SAF đã là Microservices — không cần đổi sang Monolithic

Microservices không có nghĩa là "mỗi domain nhỏ = 1 service". Định nghĩa đúng là hệ thống gồm nhiều service độc lập, có thể deploy riêng, giao tiếp qua API. SAF thỏa mãn đầy đủ định nghĩa này.

Tại sao ĐÂY LÀ Microservices

✅ Mỗi service deploy độc lập
Restart Node.js không ảnh hưởng Spring Boot. RabbitMQ giữ message trong lúc service restart.
✅ Polyglot — chọn tech phù hợp
Spring Boot cho nghiệp vụ phức tạp. Node.js cho real-time Socket.io. Mỗi service dùng DB phù hợp nhất.
✅ Giao tiếp qua API + Message Queue
HTTP qua API Gateway. Async event qua RabbitMQ. Spring Boot không biết Node.js tồn tại — chỉ biết queue name.
✅ Fault isolation
AI Service chết → chat và booking vẫn chạy. Circuit Breaker ngăn cascade failure lan sang service khác.

SAF Microservices vs Monolithic — tại sao KHÔNG nên đổi

Đổi về Monolithic là đi thụt lùi — mất đi hết những gì đã xây dựng, và bài Monolithic đơn giản thì điểm không cao bằng.

Tiêu chíMonolithic (nếu đổi)SAF Microservices (hiện tại)
Số service 1 — tất cả trong 1 ứng dụng ✅ 5 service riêng biệt
Ngôn ngữ 1 ngôn ngữ duy nhất ✅ Java + JavaScript + React (Polyglot)
Database 1 DB chung cho tất cả ✅ MariaDB (nghiệp vụ) + MongoDB (messaging)

Deploy Deploy 1 lần = deploy tất cả ✅ Deploy từng service độc lập, không downtime
Lỗi 1 service 1 lỗi = cả hệ thống sập ✅ Fault isolation — service khác vẫn chạy
Async notification Không có — phải sync ✅ RabbitMQ event-driven
Giải thích với GV Đơn giản nhưng điểm thấp hơn ✅ Phức tạp hơn nhưng điểm cao hơn nhiều
⚠️ Điều giáo viên muốn thấy ở bài Microservices
Về kỹ thuật
  • Có bao nhiêu service? → 5 service
  • Giao tiếp thế nào? → HTTP + RabbitMQ
  • Database riêng không? → MariaDB + MongoDB
  • Deploy thế nào? → Docker Compose
Về thiết kế
  • Tại sao chọn tech này? → Polyglot
  • Xử lý lỗi thế nào? → Circuit Breaker
  • Trace request thế nào? → Zipkin
  • Hướng phát triển? → Tách Auth Service

Câu hỏi giáo viên hay hỏi — và cách trả lời

Học thuộc các câu trả lời này. Trả lời ngắn gọn, tự tin, dùng đúng thuật ngữ kỹ thuật.

Q1 Bài này là Microservices hay Multi-service? Khác nhau thế nào?
Bài này là Microservices. Sự khác biệt: Microservices mỗi service có trách nhiệm riêng, database riêng, có thể deploy độc lập, giao tiếp qua API. Multi-service chỉ đơn giản là chạy nhiều process không có nguyên tắc.

SAF có 5 service riêng biệt — API Gateway (Nginx), Core API (Spring Boot), Messaging Service (Node.js), AI Service (Node.js), Web App (React/Nginx) — mỗi service có Dockerfile riêng, database riêng, deploy độc lập. Đây là Microservices.
Nhấn mạnh: "5 service, 2 ngôn ngữ, 2 database" — con số cụ thể luôn thuyết phục hơn lý thuyết chung chung.
Q2 Tại sao Spring Boot xử lý nhiều domain (Auth, Room, Booking, Payment) trong 1 service?
Đây là quyết định thiết kế có chủ ý. Room, Booking và Payment có quan hệ dữ liệu chặt chẽ và cần ACID transaction — ví dụ khi thanh toán thành công phải đổi trạng thái Booking và Room cùng lúc trong 1 transaction. Nếu tách ra thành service riêng, phải dùng Saga Pattern để xử lý distributed transaction — phức tạp hơn rất nhiều và dễ gây inconsistent data.

Nguyên tắc thiết kế: "Don't split services when they need to share transactions." Đây không phải điểm yếu mà là lựa chọn đúng đắn cho bài toán này.

Hướng phát triển tiếp theo: Tách Auth Service ra trước vì Auth không có transaction với các domain khác.
Nếu GV hỏi tiếp về Saga: "Saga Pattern chia transaction thành các bước nhỏ, mỗi bước có compensating action nếu thất bại — phức tạp hơn nhưng là giải pháp đúng cho distributed transaction."
Q3 Tại sao dùng cả Java lẫn Node.js? Không dùng 1 ngôn ngữ cho đơn giản?
Đây là Polyglot Architecture — chọn công nghệ phù hợp với từng bài toán thay vì dùng 1 công nghệ cho tất cả.

Spring Boot phù hợp cho nghiệp vụ phức tạp: JPA/Hibernate, transaction management, Spring Security, type-safe với Java.

Node.js phù hợp cho real-time: event loop non-blocking xử lý hàng nghìn WebSocket connection hiệu quả hơn thread-based model của Java. Socket.io ecosystem trên Node.js cũng trưởng thành hơn.
Thêm: "Đây là lý do các công ty lớn như Netflix, Uber dùng Polyglot Microservices — mỗi team chọn tech stack tốt nhất cho bài toán của mình."
Q4 RabbitMQ dùng để làm gì? Tại sao không gọi HTTP trực tiếp?
RabbitMQ là Message Queue — Spring Boot publish event vào queue, Node.js consume và push Socket.io cho client.

Lý do không dùng HTTP trực tiếp:
• Coupling: Nếu gọi HTTP trực tiếp, Spring Boot phải biết URL của Node.js. Nếu Node.js đổi port hay scale → phải sửa Spring Boot.
• Resilience: Nếu Node.js đang restart, HTTP call sẽ fail và throw exception trong luồng đặt lịch. Với RabbitMQ, message được giữ lại trong queue và tự deliver khi Node.js khởi động lại.
• Loose coupling: Spring Boot không biết Node.js tồn tại, chỉ biết tên queue. Đây là đặc trưng quan trọng của Microservices.
Dùng ví dụ: "Giống như gửi thư qua bưu điện — người gửi không cần biết người nhận đang ở đâu hay có nhà không, bưu điện giữ thư và giao khi người nhận sẵn sàng."
Q5 Circuit Breaker là gì? Trong bài dùng ở đâu?
Circuit Breaker là pattern ngăn cascade failure — khi một service lỗi liên tục, circuit "mở" và các request tiếp theo dùng fallback thay vì chờ timeout.

Có 3 trạng thái: CLOSED (bình thường) → OPEN (sau 5 lần fail liên tiếp, block request 30s) → HALF-OPEN (thử 3 request xem service khỏe chưa).

Trong SAF, dùng Resilience4j @CircuitBreaker bảo vệ:
• Notification publish: Nếu RabbitMQ chết, chỉ log warning — luồng đặt lịch vẫn thành công.
• VNPay gateway: Nếu cổng thanh toán không phản hồi, circuit mở và trả thông báo lỗi ngay thay vì chờ 30s timeout.
Ví dụ thực tế: "Netflix Hystrix (tiền thân của Resilience4j) được tạo ra vì 1 service chậm làm sập toàn bộ Netflix vào 2010."
Q6 Zipkin là gì? Tại sao cần Distributed Tracing?
Trong Microservices, 1 request từ client có thể đi qua nhiều service: Gateway → Spring Boot → RabbitMQ → Node.js. Khi có bug, rất khó biết lỗi xảy ra ở service nào.

Zipkin thu thập trace từ tất cả service, ghép lại thành timeline hoàn chỉnh của 1 request. Mỗi HTTP call được gắn traceId và spanId trong header — Zipkin dùng để vẽ sơ đồ.

Trong SAF dùng Micrometer Tracing + Brave (Spring Boot 3.x) — tự động instrument mọi HTTP request, không cần viết thêm code.
Tại dev: mở http://localhost:9411 sau khi chạy docker-compose — thấy ngay timeline từng request. Cực kỳ ấn tượng khi demo.
Q7 API Gateway làm gì? Tại sao không để client gọi thẳng từng service?
API Gateway (Nginx) là điểm vào duy nhất — client chỉ biết 1 địa chỉ http://localhost, không biết các service nội bộ.

Nếu không có Gateway: client phải biết port của từng service (8082, 3001, 3002...) — lộ thông tin nội bộ, CORS phức tạp, không thể scale.

Gateway xử lý: Request routing theo path (/api/* → Spring Boot, /api/messages/* → Node.js), WebSocket proxy cho Socket.io, SSL termination, Static file serving cho React SPA.
Nhấn mạnh: "Chỉ port 80 được lộ ra ngoài. Tất cả backend service dùng internal Docker network — không thể truy cập từ bên ngoài dù biết port."
Q8 Nếu tiếp tục phát triển, bạn sẽ cải thiện gì?
1. Tách Auth Service: Vì Auth không có transaction với các domain khác, đây là service dễ tách nhất. Auth Service riêng sẽ có database riêng với bảng users, otp_codes, refresh_tokens.

2. Kubernetes thay Docker Compose: Auto-scale khi traffic tăng, self-healing khi pod crash, rolling deploy không downtime.

3. ELK Stack: Tập trung log từ tất cả service vào Elasticsearch, visualize bằng Kibana — dễ debug hơn.

4. Service Mesh (Istio): Quản lý mTLS giữa các service, traffic shaping, canary deployment tự động.
Trả lời câu này tốt cho thấy bạn hiểu big picture và có tư duy kiến trúc — điểm cộng lớn.

6 Nguyên tắc cốt lõi — SAF đáp ứng thế nào

Theo định nghĩa của Martin Fowler và Sam Newman (tác giả "Building Microservices"), đây là 6 đặc trưng quan trọng nhất.

01
Single Responsibility
Mỗi service chỉ làm 1 việc — "Do one thing and do it well"
✅ Chat Service chỉ xử lý messaging · AI Service chỉ xử lý AI chat · Core API xử lý business logic
02
Decentralized Data Management (Database per Service)
Mỗi service sở hữu data của mình, không share database
✅ Core API → MariaDB (SQL, ACID transactions) · Messaging Service → MongoDB (document, flexible schema)
03
Independent Deployment
Mỗi service có thể build, test, deploy riêng mà không ảnh hưởng service khác
✅ Mỗi service có Dockerfile riêng · docker-compose restart service riêng lẻ · CI/CD pipeline độc lập
04
Design for Failure (Fault Tolerance)
Thiết kế giả định service khác có thể fail bất cứ lúc nào, không crash theo
✅ Resilience4j Circuit Breaker · RabbitMQ giữ message khi Node.js down · Health check + auto-restart · Retry logic trong Node.js RabbitMQ consumer
05
Smart Endpoints, Dumb Pipes
Logic nằm trong service, không nằm trong middleware. Giao tiếp qua REST hoặc Message Queue đơn giản
✅ Nginx chỉ route, không có business logic · RabbitMQ chỉ relay message · Mỗi service tự xử lý logic của mình
06
Infrastructure Automation
Containerization, CI/CD, health monitoring — không deploy thủ công
✅ Docker Compose với health check + condition: service_healthy · GitHub Actions CI/CD · Zipkin distributed tracing · Actuator /health endpoint
Kết luận
SAF đáp ứng đầy đủ 6 nguyên tắc cốt lõi của Microservices.
Việc Spring Boot xử lý nhiều domain là quyết định kiến trúc hợp lý (tránh distributed transaction phức tạp), không phải điểm yếu.
Đây là cách các công ty thực tế triển khai — không phải mọi domain đều cần service riêng, chỉ tách khi có lý do rõ ràng.
